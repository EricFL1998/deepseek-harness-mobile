01接入原则#

先得到完整清单，再逐项实现；每一步都有可复跑的校验。

1 · 先清单

扫描源码，得到挂载点

扫描插件注册的 slot / entry / component 与数据依赖，产出一份可执行的报告。

2 · 再实现

按形态选容器

整页用 PageContent，嵌入位用 SlotContribution； 数据走 PluginRpcHost，交互走 dispatchEvent。

3 · 可复跑

2/2 落点可验证

每补完一个落点就重跑 --check；Demo 插件的两个落点全部映射、 宿主就绪、伴生实现，可反复回归。

最佳实践

先覆盖、后像素：清单驱动实现，截图只用于视觉验收。

02整体架构#

按五步执行：插件源码 → 扫描 → UI 清单 → 原生实现 → 校验。

Host 侧

插件逻辑不动

RPC、状态、模型调用与数据查询留在 JS 插件；原生只通过 RPC 取展示数据。

App 侧

03输入与准备#

准备自己已经发布的插件包或源码仓库即可；扫描器直接读取这份输入。

输入优先级说明
lib/*.js.map首选发布包里通常带 sourcesContent，可还原原始 TSX，信息最全。
src/**/*.tsx次选开发仓库的直接源码；没有 map 时使用。
lib/client.js兜底编译产物；仍能识别 slot/entry/component，JSX 树是启发式。
原生伴侣源码可选--companion 用来判断插件 slot 是否真的被伴侣实现。
 
# 仓库根目录（App 开发环境）
python tools/plugin_ui_scanner.py --help

# SDK 交付包里也带同一份扫描器
python tools/plugin_ui_scanner.py \
  --plugin /path/to/your-plugin \
  --companion /path/to/native-companion/src \
  --write docs/plugin-ui.md \
  --json docs/plugin-ui.json \
  --check
只读插件自己的包

扫描器读插件注册信息；内置 slot 清单由 App 的 NativeSlotMapping 提供。

包名规范（强制）

伴侣 APK 统一 com.dsh.mobile.<完整插件名>：保留 dsh-plugin- 前缀，转小写，非字母数字换成 _。 包名由完整插件名直接得到：dsh-plugin-demo → com.dsh.mobile.dsh_plugin_demo。

04扫描插件源码#

一次扫描，得到插件全部 UI 挂载点与它们需要的数据。

你的插件包/ ├─ package.json name / version / 依赖 ├─ lib/ │ ├─ client.js 编译产物（兜底） │ └─ client.js.map sourcesContent 含原始 TSX（首选） ├─ src/ 开发仓库源码（次选） │ ├─ client/index.ts │ ├─ client/DemoDockChip.tsx │ └─ client/DemoSettingsSection.tsx └─ locale/*.json 文案表

扫描器识别什么

挂载点

ctx.slots.register({ name, id, order, mode }, Component)； 同时识别 slots.inject / children 关系。

数据依赖

useProjection('...')、useChat/useSession、 inject face、插件 RPC 方法名。

UI 结构

组件 JSX 树、可见文案、按钮动作、locale key； 用于确认空态、表单、提示文案都已覆盖。

定位 / 交互

useAnchoredPosition、createPortal、 anchorRef、role="dialog"、side/align 等锚定线索； 伴侣若用居中 Dialog 会提示与 anchored popover 不一致。

缺口

未映射 slot、无宿主 NativeSlot、传入 --companion 但伴侣未注册对应贡献，三类都会报。

命令示例：Demo 插件

python tools/plugin_ui_scanner.py \
  --plugin samples/demo-js \
  --companion samples/demo-native/src/main/kotlin \
  --json docs/plugin-ui-inventory-example.json \
  --check

扫描结果为 2 个落点（settings.section、conversation.composer.dock）； 两个落点都已映射、宿主就绪、伴生实现，--check 通过。报告里的「RPC 端点」 是 Web 组件实际调用的数据依赖（demo.status / demo.bump）， Host 侧完整契约还有另外 4 个端点。

05读懂扫描报告#

报告按列对应实现任务：每一行就是一条待办。

列含义怎么用
slot内置 slot 名在 NativeSlotMapping 找目标落点
entry同一 slot 下的子条目如 composer.dock 的 activity/usage，可拆独立落点
component注册的 React 组件用来读源码与确定 UI 结构
原生落点映射到的 NativeSlot为空 = App 还没认领这个位置
宿主App 是否有 NativeSlot 容器否 = 即使有映射也不会显示
原生实现伴侣是否注册贡献/页面否 = 插件有 UI、伴侣没写
数据依赖projection / RPC / inject决定原生用 PluginRpcHost 还是 spec 下发
定位/交互anchored popover / portal / dialog 等线索据此选择锚定 Popup 或 Dialog

06选择实现方式#

按形态选容器、按数据选能力；每个位置选最轻、最贴合的实现。

扫描结果原生实现典型例子
设置页 / 独立页面PageContent + PageRegistryDemo 设置页（整页接管）
输入栏、消息、dock、卡片扩展SlotContributionDemo dock 胶囊、消息动作、卡片扩展
内置控件本身OfficialSlot 包装默认 UItok/s、缓存命中、上下文、发送按钮
信息型卡片 / 列表 / 指标SpecSlotContribution + dsh-ui spec状态卡、用量面板、配置摘要
需要切模型/推理档位PluginModelHost.selectModelfast 模式按钮
暂时没有宿主显式 Web 回退未认领的新 slot
新增宿主能力

伴侣需要“切模型”或“写文件”等 App 能力时，新增可选 SDK 接口（参考 PluginRpcHost / PluginModelHost），由宿主统一注入。

07宿主能力与数据契约#

原生端只经 RPC 从 Host 取展示数据；网络与凭证留在 Host，能力由 App 注入。

PluginRpcHost

调用插件既有 RPC

rpc.callRpc(
  "demo.status",
  JsonObject(emptyMap())
) { result -> ... }
PluginModelHost

切换模型 / reasoning

host.selectModel(
  provider = "kimi",
  model = "kimi-for-coding",
  reasoningEffort = "highspeed"
)
spec

App → slot 的状态

slot spec 只放展示/选择状态，例如 modelId、reasoningEffort、 provider、displayName。

更新

refresh / 轮询

长耗时逻辑留在 Host；原生按 60s 轮询或等 client/refresh； 业务状态保留在 Host，原生按需读取。

凭证边界

token / API key / 任意文件路径只出现在 Host；原生只拿展示数据。

Popup 定位与材质

Web 版用 useAnchoredPosition / createPortal 做锚定浮层； 原生端对应使用 SDK 的 PluginPopover：贴着触发元素上方、右对齐， 材质取 App 的 DshMenuCard 映射（表面色、发丝边、16dp 圆角、菜单阴影）。

Web 线索原生实现
useAnchoredPosition / anchorRefPluginPopover，与触发元素同 Box
createPortal / role="dialog"Popup + PopupPositionProvider
side: 'top' / align: 'end'上方 6dp、右对齐、窗口内夹取
App 菜单材质colorPopupSurface / colorPopupBorder / cornerPopup
定位线索要一起扫

扫描器提取 useAnchoredPosition、createPortal、 side/align 等 placement 线索，并在伴侣用 Dialog、插件用 anchored popover 时给出告警；实现浮层时以这些线索为准。

10校验与 CI#

三道闸：插件覆盖、内置 slot 覆盖、App 单测。

Gate 1

plugin scanner --check

插件每个 slot 都有映射、有宿主、有伴侣实现，即通过。

Gate 2

slot_inventory.py

内置 slot 映射与宿主保持一致；新增内置 slot 时同步补映射、宿主与测试。

Gate 3

SlotCoverageTest

Kotlin 反射断言内置常量全集；CI 与本地一致。

# 本地 / CI 全量
python tools/plugin_ui_scanner.py --plugin <plugin> --companion <src> --check
python tools/slot_inventory.py --write docs/slot-inventory.md
./gradlew :app:testDebugUnitTest --tests com.deepseek.dsh.SlotCoverageTest
覆盖规则

新增内置 slot 时，先补映射、宿主与测试，再更新清单；每次改动保持 --check 通过。

11上线检查#

按模块逐项确认：每一项都给出正确做法与验收标准。

Slot

先补齐能力桥

slot 贡献默认只有基础 PluginHostApi；需要 RPC/模型能力时， 用 SlotBridgeHost 包装后再读取。

异步加载

让落点可观察

SlotRegistry 维护可观察 revision；APK 装载/卸载后容器自动重组。

装载

用 packageContext.classLoader

多 dex 下优先使用 packageContext.classLoader；加载异常时记录日志并降级到 Web。

数据

退避重试 + 周期刷新

首屏未就绪时退避重试（800ms / 2s）；之后按 30–60s 或 client/refresh 重读。

定位

Popup 贴锚点、限宽

用 PluginPopover，宽度 IntrinsicSize.Max，最大 320dp。

样式

材质全部取主题

浮层背景、描边、圆角、文字取 PluginTheme 的 popup 字段，和 App 菜单一致。

完整检查清单

各模块的最佳做法、检查项与验收标准见 docs/pitfalls.md。

12操作要点#

按以下顺序完成扫描、认领与验证。

确认扫描输入

插件包里准备 lib/client.js.map 或 src/*.tsx；只有编译产物时用 lib/client.js 兜底。--plugin 指向包根目录。

认领未映射 slot

在 App 侧补 DshSlotRegistry 常量、NativeSlot、 NativeSlotMapping 与宿主，然后运行 slot_inventory.py。

补宿主容器

在对应页面/控件位置加入 NativeSlot / OfficialSlot 调用。

补伴侣实现

在伴侣注册对应的 SlotContribution / PageContent， NativeSlot 与 JS 注册保持一致，然后重新扫描。

接通交互能力

需要 RPC 时确认 PluginRpcHost 由 SlotBridgeHost 注入， App 已设置 NativeHost.rpcHandler。

确认覆盖完整

以 --check、slot_inventory.py、SlotCoverageTest 为准；截图只做视觉验收。

14术语与版本#

快速查表。

术语解释
slot内置 UI 的挂载点；插件通过 ctx.slots.register 认领。
entry同一 slot 下的子条目，例如 dock 的 activity/usage；可拆成独立原生落点。
NativeSlot手机端原生容器位置；由 NativeSlotMapping 显式映射。
OfficialSlot内置控件的 slot 包装；默认内容 + 插件 ENHANCE/OVERRIDE。
PageContent整页原生 UI，注册到 PageRegistry。
SlotContribution嵌入型原生 UI，注册到 SlotRegistry。
SpecSlotContribution把 slot spec 里的 dsh-ui 结构交给 SpecRenderer 通用渲染。
PluginRpcHost调用插件既有 RPC 的宿主能力。
PluginModelHost切换模型/推理档位的宿主能力（fast mode）。
