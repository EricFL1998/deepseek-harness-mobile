# v3.2 修订：不用 Linux，把 DSH 转译到原生，可行吗？

| 项 | 内容 |
|---|---|
| 版本 | v3.2（v3.0/v3.1 的可行性补充，不改变已确认的产品目标） |
| 日期 | 2026-10-17 |
| 问题 | 能不能不要 proot/Linux，把 DSH 转译成原生（Kotlin）？ |
| 结论 | **「转译 API」可以；「转译运行时和插件」不可以。** 不用 Linux 有两条现实路线：Android 上的 Node（兼容性降级），或原生重写 Agent（放弃 Host 插件生态）。不存在「全部原生 + 插件零改动」的第三条路。 |

---

## 0. 三句话结论

1. **插件是 JS/Cordis 模块，不是协议。** 把 API 转译成原生很容易；把插件本身转译成原生等于重写整个 npm/Cordis 生态，不可行。
2. **不用 Linux 可以，但 Host 仍然需要 JS 运行时。** 现实选择是「Android 上的 Node（bionic）」——省掉 rootfs 与 proot，但原生模块、shell、平台假设会让插件兼容性明显下降。
3. **完全原生 = 放弃 Host 插件。** 原生重写 Agent 核心（12–18 人月）能换来小包体与性能，但 Host 插件（工具/技能/MCP 之外的一切）全部不可用，与「插件零改动」直接冲突。

---

## 1. 先把问题拆开

「不用 Linux + 转译到原生」实际上是三个独立问题：

| # | 问题 | 答案 |
|---|---|---|
| Q1 | 能不能不用 proot/Linux 用户空间？ | 可以：Android 上编译/携带 Node（bionic），或用原生重写 |
| Q2 | 能不能把 DSH 的 **API/协议** 转译成原生？ | 可以，已经规划（v2.0 §4 的 descriptor 生成 + 契约验证） |
| Q3 | 能不能把 DSH 的 **运行时和插件** 转译成原生？ | **不可以**（见 §5） |

关键区分：

- **协议转译**：Host 还是 JS，客户端用 Kotlin 说同一套 Remote。✅ 已有方案。
- **运行时转译**：Host 也变成 Kotlin，插件仍是 JS。❌ 除非你同时实现一个 JS 运行时去跑插件——那就不是「原生」了。

---

## 2. 四条路线对比

| 路线 | Host 运行时 | 插件兼容 | 包体 | 工期（到可日用） | 风险 |
|---|---|---|---|---|---|
| **A. proot + Ubuntu + DSH**（v3.0） | Linux 用户空间里的 Node | **高**（glibc、apt、原生模块） | 250–350 MB | 8.5–11 人月 | 中（Android 限制已知可解） |
| **B. Android Node（bionic）+ DSH** | Android 上的 Node | **中低**（纯 JS 高、原生模块低、shell 缺） | 80–150 MB | 9–12 人月 | 高（Node 构建、原生模块、exec 限制） |
| **C. 原生重写 Agent** | Kotlin | **0（Host 插件全丢）** | 30–60 MB | 12–18 人月 | 高（生态断裂、持续跟版） |
| **D. JS→Kotlin 转译** | Kotlin | 0 | 小 | 不可估 | 不可行 |

---

## 3. 路线 B：Android 上的 Node（不用 Linux）

### 3.1 能做到什么

- 用 Termux 生态或自建 Node 22/24 Android arm64 二进制，运行 DSH 的 JS 代码；
- 不需要 rootfs、不需要 proot，包体可降到 80–150 MB；
- 纯 JS 的 Host 插件、Cordis、Agent Loop、Session 都能跑；
- 客户端仍是原生 UI + Web 岛，协议层不变。

### 3.2 难点清单（按严重度）

| # | 难点 | 说明 | 对策 |
|---|---|---|---|
| B1 | **Node 本身要构建/携带** | 官方无 Android 预编译；需 Termux 二进制或自建（NDK） | 复用 Termux 包或自建流水线 |
| B2 | **原生模块（.node）** | 需 arm64 bionic 预编译：`node-pty`、`@swc/core`、`sharp`、`better-sqlite3`、`sherpa-onnx` 等 | 逐个找 Android 构建；没有就降级/禁用 |
| B3 | **Android 10+ exec 限制** | 应用私有目录里的二进制不可执行（W^X） | 二进制放 `nativeLibraryDir`（`lib*.so`）再 exec；或沿用 Termux 的 targetSdk 策略 |
| B4 | **POSIX 差异** | bionic 无 glibc、`link(2)` 受 SELinux 限制、`/proc` 语义差异 | 打补丁；接受部分功能缺失 |
| B5 | **shell 工具缺失** | 没有 bash/coreutils/git/python 的完整用户空间 | 内置 toybox/busybox + 按需下载；行为与 Linux 有差异 |
| B6 | **平台检测** | DSH 与插件可能按 `process.platform` / 路径约定判断环境 | 兼容层或补丁；随版本维护 |
| B7 | **沙箱/权限** | DSH 的 fs/sandbox 假设 Linux 权限模型 | 关闭/替换为 Android 侧策略 |

### 3.3 插件兼容分级（估计）

| 插件类型 | 估计兼容率 | 说明 |
|---|---|---|
| 纯 JS/Cordis 插件 | 高（70–90%） | 不碰原生模块与平台路径即可 |
| 含原生模块的插件 | 低（20–50%） | 取决于是否有 arm64 bionic 构建 |
| 依赖 shell/系统工具 | 中（40–70%） | 内置 busybox 可覆盖一部分 |
| 桌面专属插件 | 低（<20%） | 目录选择器、打开 App、Windows 工具 |

> 结论：路线 B 能满足「Agent 能跑、常用插件能用」，但**达不到「全部插件」**。它适合作为「轻量版/无 rootfs 版」，而不是完整版。

### 3.4 工期与风险

- Node 构建 + exec 方案：3–5 周（有 Termux 参考可缩短）。
- 原生模块逐个适配：4–8 周，且结果不确定。
- 平台/沙箱补丁：3–5 周。
- 插件兼容测试与长期跟版：持续。
- **总工期不低于路线 A**，但兼容性与确定性更差。

## 4. 路线 C：原生重写 Agent

### 4.1 必须重写的模块

| 模块 | 工作量 | 说明 |
|---|---|---|
| Cordis 插件宿主（事件/服务/生命周期） | 大 | 插件仍要 JS 才能跑；纯原生无解 |
| Agent Loop / Prompt 组装 | 大 | 插件 hook 面全部失效 |
| LLM Provider / 流式 / 重试 / 用量 | 中 | 与 provider 插件生态脱节 |
| 工具注册表 + 内置工具 + 权限 | 大 | 工具插件生态失效 |
| Session 格式 / 投影 / 查询 / 迁移 | 大 | 与现有会话数据格式脱节 |
| Compaction / Memory / Hooks | 中 | 插件可观察面 |
| MCP / Skills / Commands | 中 | 需重新实现 |
| Subagent / Workflow / Jobs | 大 | 编排与事件模型 |
| ACP / SDK / Remote 协议 | 中 | 需重新对齐 |

### 4.2 冲突点

- Host 插件通过 Cordis 事件与服务挂进上述每一层；原生重写后**插件无法观察、无法扩展**。
- 插件是 npm 包 + JS 代码；原生 App 无法加载 `.node`/JS 插件（除非再塞一个 JS 引擎，见 §5）。
- 结果是：**「完整 DSH」退化为「一个功能类似的 Agent App」**，生态不再是 DSH 的。

### 4.3 收益与代价

| 收益 | 代价 |
|---|---|
| 包体 30–60 MB | Host 插件全丢 |
| 无 proot 开销、启动快 | 12–18 人月，且持续跟版 |
| 全原生 UI/工具 | 与 DSH 会话/插件格式不兼容 |
| 设备能力直接可用 | 用户拿不到 DSH 插件生态 |

**适合场景**：你只想要「一个手机上的 Agent」，不需要 DSH 插件；那不如直接用 ACP/SDK + 自研 Agent，而不是「转译 DSH」。

---

## 5. 路线 D：JS→Kotlin 转译，为什么不可行

| 障碍 | 说明 |
|---|---|
| 动态语言语义 | 原型链、`eval`、Proxy、动态 import、闭包、异步生成器；静态转译无法保持语义 |
| npm 生态 | 插件依赖任意 npm 包（含 CJS/ESM、条件导出、原生模块）；无法整体转译 |
| Cordis 动态性 | 插件在运行时注册服务/事件/工具；原生需要等价的动态注册与隔离 |
| 原生模块 | `.node` 是编译产物，不是 JS；只能重写或桥接 |
| 版本漂移 | DSH rc 每周变化；转译产物无法跟随 |
| 工具链 | 没有工业级 JS→Kotlin 转译器；AI 辅助只适合小片段 |

**唯一可转译的是类型/协议**（descriptor、JSON schema、事件类型），这也是 v2.0 已经在做的。运行时与插件必须留在 JS。

---

## 6. 混合方案

### 6.1 原生核心 + Android Node（仅在需要插件时）

- 日常功能走原生 Agent（自己实现），插件场景启动 Android Node 兼容层。
- 问题：两套 Agent 语义会分叉；会话/工具/权限不一致；复杂度高于路线 A。
- 结论：不推荐。

### 6.2 Android Node Host + 原生 UI（路线 B）

- 去掉 Linux，保留 JS Host；UI 仍原生 + Web 岛。
- 这是「不用 Linux」的最现实折中，但插件兼容降级。
- 适合：包体敏感、能接受插件子集、愿意长期适配原生模块。

### 6.3 两种运行时不能互相替代

- Node 运行时（A/B）保证插件；原生（C）保证包体与性能。
- 你想要「完整 DSH + 插件零改动」，就只能保留 Node 运行时；Linux 只是让 Node 跑得更完整的方式。

---

## 7. 决策建议

| 你的优先级 | 选择 |
|---|---|
| **插件零改动 + 完整 DSH**（当前约束） | **路线 A（proot + Ubuntu）**，没有等价替代 |
| 包体/启动优先，可接受插件子集 | 路线 B（Android Node），先做 spike 验证原生模块与 exec |
| 只要 Agent 能力，不要 DSH 插件 | 路线 C 或直接用 ACP/SDK 自研，不要叫「DSH 手机端」 |
| 想「全原生 + 全插件」 | **不存在**；必须放宽其中一个约束 |

| # | 验证 | 通过标准 |
|---|---|---|

## 10. 补充：把「插件 API 转译到我们的实现」具体指什么？

「插件 API」不是一层，而是三层，能否原生化完全不同：

| 层 | 内容 | 能否不用 JS 原生实现 | 说明 |
|---|---|---|---|
| **声明面** | `package.json` 的 `dsh.client`、工具 schema、命令名、设置 schema、SDUI 声明 | ✅ 可以 | 客户端读取声明，用原生表单/列表/设置页渲染；**但只覆盖「长什么样」，不覆盖「做什么」** |
| **宿主 API 面** | 插件代码调用的 `ctx.*`、Cordis 事件/服务、Node API（`fs`/`net`/`child_process`/`Buffer`/streams）、npm 包 | ❌ 不能只靠实现 | 必须先有 JS 运行时执行插件代码，再把 API 绑定到原生实现 |
| **客户端 UI 面** | `client.js` 里的 React/slots/DOM | ❌ 不能 | 必须浏览器内核（Web 岛）或 SDUI 重写 |

### 10.1 只实现「声明面」会得到什么

- 可以：原生插件列表、设置表单、工具参数 UI、审批 UI、SDUI 页面。
- 不能：插件实际行为——它注册的工具如何执行、命令做什么、事件如何响应、UI 交互逻辑。
- 也就是说：**声明面原生化 = 让界面更原生；不等于插件能在原生端运行。**

### 10.2 要执行插件代码，只有两种「不用 Linux」的做法

| 做法 | 本质 | 工作量 | 兼容性 |
|---|---|---|---|
| **B1 Android Node（bionic）** | 直接用 Node 执行插件；Node 已实现全部 API | 中（构建/原生模块/exec） | 中低 |
| **B2 内嵌 JS 引擎 + 原生 API 实现** | QuickJS/V8/Hermes + 用 Kotlin 实现 `fs`/`net`/`child_process`/`Buffer`/streams + Cordis 兼容层 | **很高**（等于写一个 Node 兼容层） | 低（原生模块 `.node` 无法加载） |

B2 就是字面意义上的「把插件 API 转译到我们的 implementation」：插件 JS 跑在内嵌引擎里，API 调用落到 Kotlin。它确实能去掉 Linux，但：

- 要覆盖的 API 面很大：DSH 有 **289 个 `@deepseek-ai/*` 包（其中 62 个客户端包，约 227 个 Host/运行时包）**、约 697 个顶层依赖目录；插件还会带自己的 npm 依赖；
- Node 语义（CJS/ESM、streams、Buffer、事件循环、`process`、worker）任何一处不齐，插件就会以奇怪的方式失败；
- 原生模块（`node-pty`、`better-sqlite3`、`sharp`、`@swc/core`）在 JS 引擎里**根本无法加载**，只能重写或禁用；
- 结果：B2 比 B1 更「原生」，但**更慢、更贵、兼容更差**。

### 10.3 如果指的是「逐个把插件实现成原生」

那不是「兼容插件」，而是「重新实现每个插件」：5,000+ 插件、每个都要跟版；插件代码没有运行，也就谈不上「插件零改动」。这条路只在「自己写一个功能类似的产品」时成立。

### 10.4 结论

- 「把插件 API 转译到原生实现」如果指**声明面**：可行且有价值（原生设置/表单/SDUI），但只是 UI，不是运行时。
- 如果指**宿主 API + 插件行为**：必须保留 JS 执行；不用 Linux 的现实选择是 **B1 Android Node**，B2（引擎 + 原生 API 实现）是更贵更差的版本。
- 如果指**逐个重写插件**：不叫兼容，也不 scale。

---

> **最终判断**：不用 Linux 可以减少包体和 proot 开销，但**不能减少对 JS 运行时的依赖**。插件是 JS 生态，转译插件 = 重写生态；转译运行时 = 放弃插件。若「插件零改动」仍是硬约束，Linux rootfs 是目前唯一被验证的完整方案；Android Node 是唯一现实的「去 Linux」折中，但要接受插件兼容降级与更高的不确定性。
