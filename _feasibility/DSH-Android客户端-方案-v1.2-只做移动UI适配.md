# 方案 v1.2：API 零改动，只做移动 UI 适配

- 日期：2026-10-17
- 约束：插件全部原样使用（多为桌面布局）；手机 UI 有问题可接受；**API 必须正确**；工作量应集中在「移动 UI 适配」
- 结论：**对，这就是最省事也最稳的路线。不要重写插件 API，直接跑官方 Web 客户端，只在其上做移动适配层。**

> **v1.3 演进（2026-10-17）**：若进一步要求「核心尽量原生、不要 WebView 套壳、可转译 API」，见 [`DSH-Android客户端-方案-v1.3-Native优先.md`](DSH-Android客户端-方案-v1.3-Native优先.md)。v1.2 是纯适配路线（最稳、最快）；v1.3 是原生优先路线（工期约 4–6 人月，核心不经过 WebView）。

---

## 1. 先把「API 正确」翻译成可执行的边界

要让插件零改动、API 全对，本质上只有一条：**官方客户端原样运行**。具体到代码，就是下面这张「可改 / 不可改」表。

| 层 | 具体东西 | 能不能改 | 说明 |
|---|---|---|---|
| 插件 bundle | `/plugins/*`、`client.js`、启动图 `__DSH_BOOT__` | ❌ 不改 | 改了就是改插件，且模块图会崩 |
| 模块系统 | `window.__ModuleLoader__`、lazy CJS、平台模块表 | ❌ 不改 | 插件的 `require('react')` 依赖它 |
| 插件 API | `dsh.client`、`ctx.slots`、client services、命令/快捷键/设置注册 | ❌ 不改 | 这是「API 正确」的核心 |
| Host 通信 | `/api`、`/api/remote.mux`、`$events`、插件自定义 HTTP/WS 路由 | ❌ 不改语义 | 可以加传输层（反代/隧道），但不能改 payload 与路由 |
| 认证 | token→cookie、Host/Origin 栅栏 | ❌ 不改 | 传输层透传即可 |
| **UI 布局** | 断点、抽屉、sheet、安全区、输入区、字体/触控尺寸 | ✅ **改这里** | 移动适配的主战场 |
| **外壳** | 原生导航、通知、分享、相机、文件、生物识别 | ✅ 可加 | 原生 App 壳增强体验 |
| **单插件面板** | 某些桌面面板在手机上的兜底显示 | ✅ 可加 | 全屏 sheet / 缩放 / 横屏 / 桌面模式 |

一句话：**API 层一行不改，UI 层随便改。**

---

## 2. 架构：官方客户端 + 移动适配层（+ 可选原生壳）

```
┌─────────────────────────────────────────────┐
│ 原生壳（可选）：配对/多主机/通知/分享/相机    │
├─────────────────────────────────────────────┤
│ WebView：官方 Web 客户端（原样）              │
│  ├─ 插件模块图 / slots / client services      │
│  └─ 移动适配层（我们唯一要写的东西）          │
│       L1 全局布局 · L2 核心页精修 · L3 插件兜底│
├─────────────────────────────────────────────┤
│ 传输：局域网/TLS/隧道（只透传，不改语义）     │
├─────────────────────────────────────────────┤
│ 主机：dsh web + 全部 Host/Client 插件（原样） │
└─────────────────────────────────────────────┘
```

关键：移动适配层本身也做成一个 **DSH 客户端插件**（`dsh.client`），而不是 fork 官方前端。这样：

- 插件 API 一行不碰；
- 官方升级时只需要跟一个插件，不用 merge 整个前端；
- 桌面端自动 no-op（现有 `dsh-web-mobile` 就是这么做的，MIT 可复用）。

---

## 3. 移动 UI 适配分三层做

| 层 | 做什么 | 覆盖 | 预估 |
|---|---|---|---|
| **L1 全局移动布局** | ≤767px 断点、侧栏→抽屉、设置/文件/预览→底部 sheet、安全区、输入区防重叠、触控尺寸、横竖屏 | 所有页面一次性生效 | 1–2 周（可基于 dsh-web-mobile） |
| **L2 核心页精修** | 会话列表、聊天、输入坞、设置、模型/推理选择、审批/提问、插件市场 | 高频 80% 使用 | 2–4 周 |
| **L3 单插件面板兜底** | 桌面宽面板 → 全屏 sheet / 横向滚动 / 双指缩放 / 提示「桌面布局」 | 长尾插件 | 按需，每个 0.5–2 天 |

**这就是你说的「只要适配 mobile UI」：L1+ L2 是主体，L3 是兜底，插件代码一行不动。**

---

## 4. 哪些 UI 问题必须提前接受

| 问题 | 会不会有 | 处理 |
|---|---|---|
| 插件自绘面板桌面宽度、手机上挤/溢出 | 一定会有 | L3 兜底（全屏 sheet/缩放）；不追求完美 |
| 悬浮类插件（桌宠、挂件）在手机上挡内容 | 会有 | 允许用户隐藏/缩小；不影响 API |
| 复杂表格/代码块横向滚动 | 会有 | 横向滚动 + 字体缩小 |
| 键盘弹起遮挡输入区 | 会有 | 原生/JS 监听 viewport + 安全区处理 |
| 部分插件依赖 hover | 会有 | 长按映射 / 直接接受功能降级（UI 问题） |

这些都属于「UI 问题」，**不影响 API 正确性**。

---

## 5. 怎么验证「API 没被适配层碰坏」

| # | 验证项 | 方法 |
|---|---|---|
| 1 | 插件模块图完整 | 对比适配前后的 `/plugins` 启动图与已注册模块列表 |
| 2 | 插件命令/快捷键可用 | 在手机 UI 上执行插件注册的命令 |
| 3 | 插件自定义 HTTP/WS 可达 | 打开插件面板，抓包确认路由请求成功 |
| 4 | 插件设置持久化 | 改设置 → 重启 → 值仍在 |
| 5 | Host 工具/技能/MCP 正常 | 手机发 prompt，观察工具调用与结果 |
| 6 | 无 payload 改动 | 适配层只做布局/样式，不读写业务数据 |

只要 1–6 全绿，就说明「API 正确，只是 UI 变了」。

## 6. 工期（单人）

| 路线 | 内容 | 工期 |
|---|---|---|
| **最快** | 原生壳 + 官方客户端 + 直接内置 `dsh-web-mobile`，只做打包与少量修补 | **2–4 周** |
| **推荐** | 自研移动适配插件（L1+L2）+ 原生壳 + 传输 | **6–10 周**（约 1.5–2.5 人月） |
| **精修** | 再加 L3 长尾插件兜底、手势、平板、横屏 | 持续迭代，每周可加 1–2 个插件适配 |

对比：任何「原生重写 API」的路线（v1.1 的 S2/S3）都会把 API 风险引进来，而你现在要的恰恰是零 API 风险，所以**不需要**。

---

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 官方 UI DOM/类名随版本变，适配层断 | 只用 slot/稳定选择器；加契约探针；跟版频率约每 rc 一次 |
| 插件面板桌面布局无法通用适配 | L3 兜底 + 明示「桌面布局」；不承诺每个插件都完美 |
| WebView 内核碎片 | 最低 WebView 版本 + 特性 shim（社区已有做法） |
| 传输层改语义破坏认证 | 只做透传/反代，不改 Host/Origin/Cookie 语义 |
| 官方未来改 UI 结构 | 适配层插件化，最坏情况回退「桌面模式 + 缩放」 |

---

## 8. 建议的落地顺序

1. **第 1 周**：官方客户端跑进 WebView；装 `dsh-web-mobile`；验证 5 类插件 + 6 条 API 验证。
2. **第 2–3 周**：原生壳（配对/连接/返回键/安全区/下载/分享）+ 传输层（局域网/TLS）。
3. **第 4–6 周**：自研适配插件接管 L1（不依赖第三方）；L2 精修会话/输入/设置。
4. **第 7 周起**：L3 按真实插件使用频率逐个兜底；建立每版 DSH 的回归清单。

**你的判断是对的：把力气全花在 UI 适配上，API 一行不碰，是这个需求下投入产出比最高的方案。**
