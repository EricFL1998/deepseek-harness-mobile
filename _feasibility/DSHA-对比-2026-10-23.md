# DSHA vs DSH 手机端：对比报告

- 日期：2026-10-23
- 对比对象：`https://github.com/DSH-APP/DSHA`（HEAD `326be52`，MIT） vs 本仓库 `deepseek-harness-mobile`
- 方法：浅克隆 DSHA 源码与文档，阅读其 README / AGENTS / security-model / virtual-screen 文档及设备层源码；对照本仓库的模块、Manifest、`BridgeServer`、`ProotCommandBuilder`、rootfs 清单与 README。
- 说明：本报告只比较当前源码事实，不评价两个项目的发布质量；DSHA 的文档里包含大量验收记录，这里不复述。

## 0. 一句话结论

两者都把**同一版本（DSH 0.2.1-rc.2）的完整 Host** 塞进 Android，但产品路线相反：

- **DSHA = “WebView 启动器 + 手机操控层”**：界面是手机上的官方 Web UI（加 `dsh-web-mobile` 适配），核心卖点是 **agent 能真正操作这台手机**（无障碍、无线 ADB、Shizuku/Root、虚拟屏、MCP 工具）。
- **我们 = “原生 Compose 客户端 + 插件 UI 框架”**：聊天、侧栏、文件、插件商店、审批、终端等核心界面原生实现，Host 插件通过 `bridge/v1` 映射成原生 slot，另有 Native UI SDK 让插件用 Compose 写原生界面。手机操控能力目前基本空白。

一句话：**DSHA 强在“手机是 agent 的手”，我们强在“手机是 DSH 的原生客户端”。** 两者的 Host 能力同源，差异主要在 Android 壳层。

## 4. 手机操控能力（重点）

这是两个项目差距最大的部分。DSHA 把“让 agent 操作手机”当成一等能力，我们目前只有一个 5 方法的设备桥。

### 4.1 DSHA 的能力分层

| 层 | 实现 | 关键事实 |
|---|---|---|
| 设备桥 | `HttpShellService`（约 105 KB，`127.0.0.1:3090`） | 30 余条路由（README 概括 `/app/*` 24 个端点）；`X-Token` 门控，token 在容器内 `/root/.dsh/.bridge_token`；loopback |
| 无障碍 | `DshaAccessibilityService` | `uiDump / uiTap / uiTapText / uiInput / uiKey / uiSwipe / uiScreenshot`，支持虚拟屏转发；**不需要 ADB** |
| 无线 ADB | `AdbBridge` + `assets/adb-pair.py`、`adb-shell.py`、`adb-setup.sh` | 在 rootfs 内用 Python + `adb_shell_wifi` + SPAKE2 完成 **TLS 1.3-PSK + SPAKE2** 配对；不需要 Shizuku；Android 11+；保活/重连；拿到 `uid=2000(shell)` |
| Shizuku / Root | `ShizukuShell` / `RootShell` | 备用特权通道，与 ADB 共用同一套命令白名单 |
| 虚拟屏 | `vscreen/` + 特权 `app_process --launch` Core | Standard / API 30+；必须先授权 ADB/Shizuku/Root 之一；`VirtualDisplay` + `ImageReader` + 指定 display 输入注入；不是模拟器 |
| MCP 工具 | `dsh-computer-use-android`、`dsh-tool-vscreen` | 模型直接调用 `android_get_state / android_screenshot / android_click / android_type / android_key / android_swipe` 等；坐标触控必须带新鲜 `observationId`（30 秒、一次）；虚拟屏用 `android_vscreen_*` |
| Agent 技能 | `agent-skills/device-shell`、`agent-skills/screen-ocr-operator` | 教 agent 用 ADB/Shizuku/Root 三通道，以及截屏 + OCR + 批量屏幕操作 |
| 命令策略 | `util/DeviceShellPolicy` + `assets/device-shell-policy.py` | 白名单默认拒绝；格式化/分区/SELinux/系统属性写入直接拒；不认识的命令不放行；写路径限制在共享存储子路径与 `/data/local/tmp`；返回 `[POLICY_BLOCKED]` + 退出码 126，没有“仍然允许”按钮 |

- 屏幕/UI：`/app/ui/*`（dump、tap、input、key、swipe、screenshot）、`/app/vscreen`
- 应用：`/app/apps`、`/app/launch`
- 交互：`/app/notify`、`/app/toast`、`/app/vibrate`、`/app/ask`、`/app/share`、`/app/open`、`/app/overlay`
- 文件：`/app/readfile`、`/app/export`
- 设备：`/app/device`、`/app/sensors`、`/app/sensor`、`/app/location`、`/app/torch`
- 剪贴板：`/app/clip`
- 命令：`/exec`（设备命令）、`/confirm`、`/consent/policy`
- 其他：`/app/version`、`/app/help`、`/app/plugins`、`/app/task/*`（任务通知/上下文）

## 6. 安全模型

| 维度 | DSHA | 本仓库 |
|---|---|---|
| 设备命令 | 三通道共用白名单；默认拒绝；写路径限制；`[POLICY_BLOCKED]` | 无设备命令层 |

## 8. 各自优势与短板

**DSHA 优势**

- 手机操控能力完整：无障碍 + 无线 ADB + Shizuku/Root + 虚拟屏 + MCP 工具 + 白名单，形成闭环。
- 离线安装、无网可用；rootfs 内置，首次体验好。
- 可靠性工程深：备份/恢复/应急/试运行回切/诊断。
- Web UI 路线让官方界面与插件页零重写。
- 测试与文档密度高。

**DSHA 短板**

- 主界面是 WebView，性能、焦点、键盘、弹窗、PiP 等都要补丁；原生交互上限低。
- 插件 UI 只能是 Web，没有原生插件能力。
- 单模块 Java、1000+ 文件，长期维护成本高。
- 仅 arm64、APK 278 MB。
- 设备能力权限重（无障碍、QUERY_ALL_PACKAGES、短信等），上 Google Play 基本不可行（DSHA 走 GitHub/爱发电分发）。

**我们的优势**

- 原生 Compose 体验：聊天、审批、文件、插件商店、侧栏、终端都是原生。
- 插件原生 UI：`bridge/v1` slot 映射 + Native UI SDK + 伴生 APK，是 DSHA 没有的差异点。
- 多模块、Kotlin、APK 小、支持 x86_64、minSdk 26。
- 已有语音 STT、原生文件/预览、Agent Team/定时任务原生界面。

**我们的短板**

- 手机操控几乎为零，且桥无鉴权。
- 首次安装要下载 305 MB rootfs，无离线安装。
- 无 proroot、无 LAN、无 PiP/悬浮条、无恢复环境。
- 远程/多 Host 仍是占位；测试与文档密度远低于 DSHA。

**建议路线**：先补 P0（鉴权 + 白名单），再做 P1（无障碍 + MCP 工具），这两步就能让“agent 操作手机”成立；ADB 和虚拟屏是增强项，按需求再上。不要在没有白名单和鉴权的情况下先开 ADB/Root。

## 10. 结论

- 两个项目的 **Host 同源、壳层分叉**。DSHA 把 Android 当成 agent 的执行环境；我们把 Android 当成 DSH 的原生前端。
- DSHA 的手机操控实现是当前最完整的公开参考：无障碍、无线 ADB、Shizuku/Root、虚拟屏、MCP 工具、白名单六件套，且互相约束。
- 我们要补的不是“照抄 DSHA”，而是 **在自己的 bridge 插件体系里补一条设备能力通道**：鉴权 → 白名单 → 无障碍 → MCP 工具，再考虑 ADB/虚拟屏。
- 远程能力两者都还没有“手机控制桌面 DSH”；DSHA 的 LAN 代理解决的是反方向。我们的多 Host 设计仍需单独实现。

## 11. DSHA 的工程解法：工作区 / bash / proot

这一节回答“DSHA 具体怎么解决 Android 上的工作区、bash 和 proot 问题”。它的做法可以概括为：**把 DSH 完整地放进一个受控的 proot 世界，workspace 默认放在应用私有目录，bash 自然在这个世界里跑；Android 侧只提供文件和设备能力的出入口。**

### 11.1 proot：先解决“能稳定跑”，再谈性能

- **执行入口**：`libproot.so` 从 `nativeLibraryDir` 执行，不复制到可写目录（Android 10+ 的 W^X 限制）；启动参数为 `-L --kill-on-exit -0 --rootfs=<私有根> --cwd=/root`，再追加显式 bind。
- **假 root**：`-0` 只让 guest 看到 root 身份；Android 内核仍按应用真实 UID、SELinux 与权限执行。文档明确不把它当安全沙箱。
- **bind 清单**：`/dev`（含 `/dev/urandom → /dev/random`）、`/proc`、`/sys`、`/system`、`/apex`、`/proc/self/fd → /dev/fd`、`/storage/emulated/0 → /sdcard` 以及同路径映射；缺失源记录 `BIND_SKIPPED`；**故意不绑定 `/linkerconfig`**（SELinux 下无权限，只会污染日志）。
- **硬链接**：`RuntimeHardlinks` 在 rootfs 的独占槽位里真实探测 `link(2)`；只有不支持时才加 `--link2symlink`，并把 `.l2s` 目录按宿主绝对路径 bind 进容器、设置 `PROOT_L2S_DIR`。这样在 ext4/f2fs 上保持原子发布语义，不会为兼容无条件打开 link2symlink 而破坏 `write` 工具的 hardlink 发布。
- **加载器与环境**：`PROOT_LOADER`、`PROOT_LOADER_32`、`PROOT_TMP_DIR`、`LD_LIBRARY_PATH`；`libtalloc.so.2` / `libandroid-shmem.so` 从随包原生库准备；`PROOT_NO_SECCOMP=1` 是显式可选项。
- **16 KB 页**：原生 session launcher 同时做 4 KiB/common 与 16 KiB LOAD 对齐；文档明确“对齐检查不等于所有 16 KiB 手机实测通过”。
- **proroot 备选**：5 个 vendor `.so` + 2 个自有兼容 ELF；proroot 没有 `--kill-on-exit`，所以停止必须按 PID + 出生身份核验，不能只杀 launcher 或按端口反查。
- **启动/停止的可观测性**：`/bin/bash -c` 包一层固定启动命令；`$$` 写 PID 文件、停止哨兵文件、启动代次；`WebProcSel` 识别 dsh 进程且绝不误杀 proot 启动器；退出未知时保留维护屏障，不重放。
- **数据与运行环境分离**：rootfs 在 `files/linux/ubuntu`；用户数据在 `user-data-v5/dsh`（稳定布局）并通过 `UserDataBindings` 把宿主目录 bind 到 guest 的 `/root/.dsh`；受管文件在 rootfs 内逐个 bind 覆盖。这样重打/升级运行环境不会把会话和配置一起换掉。
- **DNS/CA**：`dns-compat.cjs` 预加载、`SSL_CERT_FILE`/`NODE_EXTRA_CA_CERTS` 等统一指向随包 CA，`npm_config_prefix`、`NARB_DISABLE_NATIVE_CACHE=1` 也在统一环境里设置。

### 11.2 工作区：默认私有，外置只做引用

- **默认工作区在应用私有目录**：`WebLaunchCommand` 固定 `DSHA_WORKSPACE_DOCUMENTS=/root/Documents`；`workspace-directory-policy-patch.json` 把 DSH 的 `defaultWorkspaceDirectory` 在满足条件时改成 `/root/Documents`。这是 ext4/f2fs，硬链接与原子写入正常，避开 FUSE 上 `link(2)` 直接 EPERM 的那类问题。
- **外置工作区**：`/sdcard` 与 `/storage/emulated/0` 是 bind 进来的，用户在 DSH 的 Web 目录选择器里可以选 Android 共享存储下的项目；外置目录只维护“私有引用”，维护/清理不遍历、不删除、不改名其内容，备份也不自动扫描外置内容。
- **目录选择器的真实故障与修复**：DSH `WorkspaceController` 默认组合在手机上有 registry hydration 依赖问题，`directoryPicker/list` 会返回 `gateway/service-unavailable`；`directory-picker-service-patch.json` 把 `DirectoryPickerController` 独立挂载，再挂原 `WorkspaceController`，保留原有 schema、鉴权、后端能力检查，不伪造 service。这是“先修组合，不绕协议”的典型做法。
- **原生文件出入口**：
  - `DshDocumentsProvider` 把私有 Linux 树暴露给 Android 文件管理器（MT 管理器等）；
  - `WorkspaceFilesActivity` 通过 DocumentsProvider 只读浏览工作区，再经 SAF 保存/分享；
  - Web 端的 `web-integration/files.js` 用 `DshFiles` WebMessageListener 处理下载/分享（限制 32 MiB share、2 GiB save），避免让网页直接摸 Android 文件系统；
  - `WorkspaceFileExports` / `DownloadsExport` 负责导出到 `Download/DSHA`。
- **数据与备份**：一键备份包含对话、设置、插件和当前应用内工作区；外置工作区要用户另外备份；备份先安全停止 DSH 和任务，恢复先做认证/摘要/预检，再写编号槽位。

### 11.3 bash：没有“绕出去”，就在容器里跑

- DSH Host 本身跑在 proot 的 Ubuntu 里；`dsh-tool-bash` 通过 `ctx.shell` 在**同一个 guest**里执行 `/bin/bash`，没有 Android bridge、没有“每条命令再起一个 proot”。
- `RuntimeLauncher` 把 runtime argv 后面统一接 `/bin/bash -c <command>`，环境固定 `HOME=/root`、`PATH=/root/dsh-bin:...`、`TMPDIR=/tmp`、`DEBIAN_FRONTEND=noninteractive`，再叠加 CA/DNS/Node preload。
- bash 工具本身只被补了两件事：`dsha-destructive-policy` 的全局确认与命令预检（`guard-bash-patch.json`），以及 `preparedEnvironment`；没有改执行位置。
- Android 设备命令是**另一条链路**：`/exec` 通过 ADB / Shizuku / Root 通道执行 `/system/bin/*`，由 `device-shell` / `screen-ocr-operator` 技能使用；它和 DSH bash 不混用。设备桥 `:3090` 用 `X-Token` 门控；`bridge-token-compat.cjs` 只在 Node preload/早期浏览器脚本里把 `127.0.0.1:3090` 的 GET `?token=` 窄迁移成 `X-Token` 头并删除 query，不放开 CORS。
- **为什么能这样**：proot 的 bind、`-0`、`--kill-on-exit`、条件 link2symlink、loader/env 都到位后，Node 的 subprocess provider 可以在 guest 内正常 spawn `/bin/bash`；这正是 DSHA 不需要 bash 桥的前提。
- **终端**：Termux `terminal-emulator` JNI 真 PTY，复用同一套 runtime argv/env，起 `/bin/bash -l`；与 Web 的 bash 工具共享同一个文件系统和环境，但进程生命周期独立管理。

### 11.4 与我们实现的差异（直接对照）

| 维度 | DSHA | 我们 |
|---|---|---|
| DSH bash 执行位置 | Host 容器内 `ctx.shell` → `/bin/bash` | 打了 bridge 补丁：Host 通过 `android_exec_shell` 让 App 侧再起一个 proot 执行 |
| bash 与 DSH 语义 | 保留 background jobs、sandbox policy、shellEnv、取消与 jobs 记录 | bridge 分支在 `run_in_background` 判断之前返回；绕过 DSH 的 jobs / sandbox policy / shellEnv |
| 默认 workspace | `/root/Documents`（应用私有 ext4，硬链接/原子写正常） | `/storage/emulated/0/Documents/DSH-Workspace` bind 到 `/workspace`（FUSE，需要 fs.link 兜底补丁） |
| 工作区文件出口 | DocumentsProvider + 只读 WorkspaceFilesActivity + SAF 导出/分享 | 共享存储直接可见 + 原生文件浏览/预览 |
| 数据位置 | 稳定布局把 `user-data-v5/dsh` bind 成 `/root/.dsh`，与 rootfs 分离 | `/root/.dsh` 在 rootfs 内；rootfs 重装前做备份 |
| proot 参数 | `-0`、`--kill-on-exit`、`/system`、`/apex`、fd 绑定、硬链接探测后按需 `--link2symlink` | 无 `-0`/`--kill-on-exit`；Host 不加 link2symlink；exec 加；绑定较少 |
| 停止 | PID + 出生身份 + 哨兵；不按端口/裸 PID 杀 | 清理/proot 进程按 cmdline 扫描 + runner 状态；身份核验较弱 |
| 目录选择器 | 独立挂载 DirectoryPickerController 修组合故障 | 原生 UI 自行选目录，没有 DSH 目录服务问题 |
| 设备桥 | X-Token + 窄 fetch 兼容；设备命令白名单 | 本轮刚加 token；还没有命令白名单 |

### 11.5 可以直接借鉴的点

1. **把 bash 移回 Host 容器**：先对照 DSHA 的 proot 参数与 bind 清单补齐（`-0`、`--kill-on-exit`、`/system`、`/apex`、fd），再删掉 bash 的 bridge 分支；这样 background jobs、sandbox policy、shellEnv、取消语义都会回来。迁移前要单独验证 proot 内 subprocess spawn 与长命令/取消。
2. **数据与 rootfs 分离**：把 `/root/.dsh` bind 到 `files/user-data-v5/dsh`，rootfs 更新不再依赖“先备份再恢复”。
3. **workspace 默认私有，外置按需**：私有 ext4 默认值能避开 FUSE 的 link/原子发布问题；外置目录用 bind + 引用管理。若保留共享存储默认值，就要继续维护 fs.link 兜底并明确告知风险。
4. **硬链接探测**：不要无条件开 `--link2symlink`；先探测，再决定，并绑定 `.l2s` 路径，保护 `write` 工具的原子发布。
5. **停止语义**：PID 文件 + 出生身份 + 停止哨兵；不要按端口/名称/裸 PID 杀（我们目前是 cmdline 扫描，容易误伤）。
6. **目录服务组合修复**：如果要接 DSH 官方目录选择器，按 DSHA 的方式独立挂载 `DirectoryPickerController`，不要改 Gateway 鉴权或伪造 service。
7. **文件出入口用 DocumentsProvider + WebMessageListener**：比把共享存储直接暴露给 WebView 更容易控制权限与大小。
